1 · Put the admin account lifecycle in one deep module

Strong in-process

application/usecase/ApproveAdminCommand.kt · DisableAdminCommand.kt · ReactivateAdminCommand.kt · RejectAdminCommand.kt · AdminManagementSupport.kt · domain/AdminUser.kt

Problem. Four shallow twin commands each wrap the same 3-step shape; the legal status transitions, audit stamps and the “owner is not disableable” rule are enforced by callers, so the AdminUser module has no depth and understanding the lifecycle means bouncing across five files — poor locality.

Solution. Give AdminUser a deep transition(target, by, at) that knows the legal transitions and stamps audit fields; collapse the four commands into one ManageAdminAccount use case behind a single inbound port. The REST adapter maps verb → operation. Keep requireOwner() — that guard is a real shared seam.

2 · Merge parallel admin/team session twins

Worth exploring local-substitutable

application/usecase/AdminSessionIssuer.kt · TeamSessionIssuer.kt · AuthenticateSessionQuery.kt · AuthenticateTeamSessionQuery.kt · domain/SessionTokens.kt

Problem. Two parallel shallow trees nearly identical modulo adminUserId ↔ teamId; “hash on write, compare on read” and expiry semantics exist twice with slight wording — a drift risk. SessionTokens is already a good seam.

Solution. Extract one SessionMaterializer behind the existing SessionTokens seam, parameterized by a SessionRecord interface both session types implement; one sweeper path for both. Do not merge the authenticators’ business rules (admin status re-read is admin-specific).

3 · One seam for “owned team of an owned tournament”

Strong in-process

application/usecase/OwnedTournamentLookup.kt · ManageTeamAccessLinkCommand.kt · CreateTeamCommand.kt · 9 further command files calling findOwnedOrThrow

Problem. The most repeated rule in the app lives as an incantation at the top of every command; the compound “owned tournament AND team belongs to it” check is re-implemented in two places — callers can drift, and any policy change means a shotgun edit.

Solution. One deep helper OwnedTeamAccess.requireOwnedTeam(tournamentId, teamId, owner): Team used by every team verb; treat the tournament lookup as its private detail. Test that seam once instead of re-asserting ownership per command.

4 · Group verbs per aggregate instead of one file per use case

Worth exploring in-process

application/api/ (36 interface files) · application/usecase/ (~36 command classes) · UseCaseConfiguration.kt (261 lines of @Bean wiring)

Problem. Maximum granularity: simple verbs get shallow interface/implementation pairs, and the 261-line configuration is the symptom — it stitches ~36 beans whose wiring carries no information. Every new verb costs three new files plus a bean.

Solution. Group cohesive verbs into one port + one use-case class per area (TeamCommands, TournamentCommands, AdminAccountLifecycle…). ManageTeamAccessLinkCommand is the model to copy: three interfaces in 97 lines, reads well. Do it opportunistically per aggregate, not big-bang.

After — deep module per aggregate

  • Locality: “what can happen to a team” is one file
  • Bean wiring collapses in bulk
  • Hexagonal rule preserved — just coarser modules

5 · One deep mutation hook for the owner console

Strong local-substitutable

features/owner-console/hooks/owner-console-queries.hook.ts (8 clone hooks) · use-console-action.hook.ts · admin-api/admin.repository.ts (module singleton)

Problem. Eight shallow hooks differing only in repository function and key, plus a second, parallel error-capture mechanism in useConsoleAction — components carry two error paths and the bug-prone wiring lives in each component, not in the tested helper. The repository singleton is not injectable, so the seam can’t be stubbed without module mocking.

Solution. One factory hook useAdminAction(fn, queryKey) returning { run, error, isPending }, folding useConsoleAction into it so TanStack mutation state is the single error source. Make the repository injectable once, centrally, in test-helpers.

6 · One typed-request helper across the four API slices

Worth exploring ports & adapters

admin-api/ · auth-api/ · team-api/ · tournament-api/ (each: repository + dtos + mappers) · shared/api/api-client.ts

Problem. Every repository function repeats the identical 3-line choreography get → zod parse → mapper; the pattern is enforced by convention only, so one slice could silently forget parse or mishandle a status. The mappers themselves are appropriately deep and tested — keep those.

Solution. One request(path, schema, mapper) helper in shared/api; each slice becomes a table of endpoint configs. Per-slice files stay for locality of DTOs/mappers — only the call choreography collapses.

Top recommendation

Start with Candidate 1 — the admin account lifecycle. It is the smallest change with the highest concentration of currently scattered domain rules: the legal transitions, audit stamps and owner-guard all move next to the domain type they govern. It passes the deletion test cleanly (complexity concentrates, nothing just moves), and it composes with Candidate 4’s grouping — the merged ManageAdminAccount is the first aggregate to group. Pair it with the frontend Candidate 5 if you want one backend and one frontend deepening in the same pass.
